# Course overview

The design rationale. Read this if you are teaching the course, adapting it, or
wondering why something is the way it is.

---

## The argument

The course makes one argument in ten steps:

| stage | question | tutorials |
|---|---|---|
| **A** | How did machine learning work before deep learning? | 01 |
| **B** | What changed when models learned their own representations? | 02, 03 |
| **C** | What changed with self-supervision and attention? | 04, 05, 06, 07 |
| **D** | What changed with foundation models? | 08, 09, 10 |

Stated as a progression a student should feel is inevitable by the end:

> In classical ML we trained a model to solve a task.
> In deep learning we learned the representation the task needed.
> With self-supervised learning we learned useful representations *before*
> knowing the downstream task.
> With Transformers we got an architecture that learns rich contextual
> representations at scale.
> With foundation models we pretrain reusable representations of an entire
> domain.

So the question stops being *"which neural network should I train for this
power-system problem?"* and becomes *"what reusable representation of the power
system should be pretrained, and how do I adapt it safely to this grid and this
task?"*

## Design decisions, and why

### The optional eleventh tutorial

Tutorials 01–10 are the onboarding course and are self-contained. Tutorial 11
(*Federated Learning and Federated Foundation Models*) is marked
**optional / advanced** and sits outside that arc deliberately: it introduces a
second, independent axis.

```text
                     CENTRALIZED DATA        FEDERATED DATA
                            │                      │
Task-specific model         │  Tutorials 01-03     │  FedAvg, FedProx      (11)
                            │                      │
Foundation model            │  Tutorials 08-10     │  Federated foundation (11)
                            │                      │  model
```

The vertical axis is *model generality* — the whole of 01→10. The horizontal
axis is *where the data lives*, and nothing in 01–10 touches it. Keeping them
separate is the point: a reader who conflates "foundation model" with
"decentralised training" has misunderstood both.

The full progression, with the second axis appended:

```text
Task-Specific ML → Neural Networks → Representation Learning → Attention
    → Transformers → Foundation Models → Domain Foundation Models
    → Grid Foundation Models → Federated Grid Foundation Models   (optional)
```

```text
CENTRALIZED DATA → DISTRIBUTED DATA → FEDERATED TRAINING
    → PRIVACY-ENHANCED FEDERATED TRAINING                          (optional)
```

### One dataset, ten notebooks

Tutorials 01–09 forecast the same series — day-ahead system load, same split,
same test period — so the models are directly comparable and a shared
leaderboard fills up as the course proceeds. Using a fresh toy dataset per
notebook would have been easier to write and would have destroyed the
narrative.

The leaderboard (`data/artifacts/leaderboard.json`) only ever contains rows from
experiments that were actually executed. A tutorial a student skips leaves a
gap, not a fabricated number.

### Build it, then use it

Every notebook alternates:

| built from scratch | then replaced by |
|---|---|
| least squares by normal equation | `sklearn.LinearRegression` |
| backpropagation in NumPy, gradient-checked | `loss.backward()` |
| attention in NumPy, checked against PyTorch | `nn.MultiheadAttention` |
| a Transformer block, assembled piece by piece | `TransformerForecaster` |
| a character-level GPT | a pretrained LLM from the Hub |
| a task-specific forecaster | a zero-shot foundation model |
| message passing with `index_add_` | (PyTorch Geometric, signposted not used) |

The rule for what lives in `src/` versus the notebook: **if moving code into the
package would hide the idea being taught, it stays in the notebook.** The
package holds the dataset, the metrics, the training loop and the model
definitions — the things that would otherwise be copy-pasted ten times.

### Synthetic data, stated loudly

The committed dataset is simulated. It is built from solar geometry, a turbine
power curve, a temperature-driven load model and a merit-order price stack, and
its magnitudes are tuned to Germany. Every notebook prints a provenance banner.

This was a licensing decision, not a pedagogical one — see `data/README.md` —
but it turned out to have two teaching benefits:

1. **Data provenance becomes the first thing tutorial 01 does**, rather than an
   appendix nobody reads.
2. **Tutorial 09 gets a contamination-free zero-shot evaluation.** Chronos-2's
   pretraining corpus certainly contains public electricity data; it cannot
   contain a series generated by this repository. That is a genuinely clean test
   and almost impossible to arrange with public benchmarks.

### CPU by default

The lockfile pins the CPU build of PyTorch. Every notebook runs on a laptop.
Nothing needed for completion requires a GPU. This costs some realism — tutorial
06 measures the Transformer being *slower* than the LSTM on four threads, which
is true and instructive — and buys the guarantee that a student can actually run
the course on the machine they have.

### Prose follows measurement

Several notebooks were rewritten because the experiment disagreed with the
expected story:

- The MLP in tutorial 02 **beat** gradient boosting, so the text argues
  "competitive, not transformative" rather than the folk claim that trees always
  win on tabular data.
- The vanishing-gradient demo in tutorial 03 showed a default-initialised LSTM
  decaying as fast as a vanilla RNN — so the notebook teaches forget-gate bias
  initialisation, which is a better lesson than the one originally planned.
- Tutorial 03's first failure hypothesis (recent volatility predicts error) was
  **wrong**, with $r = -0.07$. It is reported as a failed hypothesis alongside
  the one that held.
- Tutorial 06 measures the Transformer training slower than the LSTM and
  explains why, instead of repeating "Transformers are faster".
- Tutorial 04's label-efficiency gain is a few percent, not a landslide, and the
  text says so and explains what would make it larger.

If you adapt the course and your numbers move, **rewrite the prose, not the
experiment.**

### The measured results the text depends on

Regenerating the notebooks on a different machine will move these a little. If
one moves *a lot*, the surrounding prose needs rewriting, not the experiment.

| where | result |
|---|---|

| 02 | MLP 1624 MW vs. gradient boosting 1785 MW — competitive, not transformative |

## What is deliberately not here

| omitted | why |
|---|---|
| PyTorch Geometric | message passing is ten readable lines of `index_add_`; PyG is signposted for real work |
| Hugging Face `datasets` | a plain torch loop is smaller and shows more |
| `Trainer` / Lightning | the training loop is the thing being taught |
| CNNs in depth | mentioned in the timeline and glossary; the domain thread is time series and graphs, and a full CNN tutorial would cost a notebook that tutorial 10 needs |
| RLHF / DPO implementations | conceptual treatment in tutorial 07; implementing them is a course of its own |
| diffusion models | named where relevant (GenCast, EnergyDiff), not implemented |
| distributed training, MLOps, Kubernetes | explicitly out of scope — the repository must stay readable |
| commercial APIs | nothing requires a key |

Terms a student should *recognise* after the course without a dedicated tutorial:
scaling laws, data contamination, benchmark leakage, RLHF, preference
optimisation, hallucination, context windows, mixture of experts, quantization,
LoRA, multimodality, tool use, agents, retrieval, state-space models, diffusion
models. Each appears in context with a citation.

## Scientific practice woven through

Rather than a "responsible AI" appendix, these appear where they bite:

| theme | where |
|---|---|
| data provenance | 01 (banner), `data/README.md` |
| leakage | 01 (measured across three model capacities), tested in `tests/` |
| baselines | 01 (and every leaderboard entry since) |
| uncertainty / calibration | 09 (CRPS, pinball, coverage) |
| out-of-distribution behaviour | 09 (domain shift), 10 (held-out topology) |
| physical validity | 01 (night-time PV), 10 (power-balance residual) |
| interpretability limits | 05 (attention ablation), 02 (weight-magnitude caveat) |
| memorisation and privacy | 07 (verbatim overlap measurement) |
| licensing | 08 (model licences), `data/README.md`, `LICENSE` |
| compute cost | 06 (timings), 08 (quantization arithmetic), 09 (latency) |
| deployment bar | 10 (why a notebook benchmark licenses nothing) |

## Suggested schedules

**Semester course, 12 weeks.** One tutorial per week, 90–120 minutes contact
time; weeks 11–12 for a student project. This is the intended shape.

**Intensive block, 5 days.** Two tutorials per day; drop tutorial 07's scaling
sweep and tutorial 06's depth study to fit. Day 5 is tutorial 10 plus
presentations.

**Self-study.** In order, at whatever pace. Budget roughly 2–3 hours per
notebook including the exercises, and do not skip 04 — everything after it
depends on the label-efficiency argument.

**A two-hour seminar.** Tutorials 01, 09 and 10, with the theory sections read
in advance. This is the "why should I care" path and it works, but students
will not have built anything.

See [`instructor_guide.md`](instructor_guide.md) for per-notebook timings,
likely difficulties and discussion questions.

## Where to go next

The course stops at a deliberately unfinished point. Natural continuations:

- **Real data.** Run everything on OPSD (`scripts/download_data.py`) and report
  which conclusions survive.
- **Real grids.** `uv sync --extra simbench` and redo tutorial 10 on German
  MV/LV benchmark networks.
- **The grown-up version of tutorial 10.**
  [`gridfm-graphkit`](https://github.com/gridfm/gridfm-graphkit) and
  [`gridfm-datakit`](https://github.com/gridfm/gridfm-datakit) implement the
  same methodology at research scale.
- **Other time-series foundation models.** Swap Chronos-2 for TimesFM, Moirai or
  TinyTimeMixers in tutorial 09 and compare.
- **The benchmarks.** arXiv:2604.22077 and arXiv:2604.22328 evaluate
  time-series foundation models on power-system tasks and do not entirely agree
  with each other. Reading them together is the assignment tutorial 09 ends on.
